# Codex 用量预测：开发说明

更新日期：2026-11-10。本文记录当前设计约束、源码入口、更新方式和待验证事项。详细公式与参数见[额度预算算法](./额度预算算法.md)。

## 项目概况

| 项目 | 当前状态与依据 |
| --- | --- |
| 产品形态 | Codex 桌面侧边栏 MCP App 页面，同时显示 5 小时和周额度。 |
| 当前源码 | `0.1.29`，可在 `plugin.json`、`server.mjs` 和页面 `appInfo.version` 中核对。 |
| 插件身份 | 市场 `codex-local-tools`；插件 `codex-usage-panel`；工具 `usage.dashboard`、`usage.read`；当前资源 `ui://codex-usage-panel/dashboard-v0.1.29`。 |
| 项目目录 | 仓库根目录下的 `codex-usage-panel/`；实际插件源码位于其 `plugins/codex-usage-panel/` 子目录。 |
| 市场清单 | 项目根目录的 `.agents/plugins/marketplace.json`，注册时必须使用该项目目录。 |

## 已确认的设计约束

- 必须保留市场名 `codex-local-tools`、插件名 `codex-usage-panel` 及现有工具与页面入口身份，除非用户明确要求变更。
- 交付必须保留 Codex 桌面侧边栏 MCP App 页面。算法与界面修改必须以项目中的源码为准，不得直接修改已安装插件缓存。
- 同时直观看到 5 小时与周额度，包括当前用量条、走势、重置时间和倒计时。
- 绿色已用曲线必须来自实际历史额度快照，并做轻度平滑。样本不足时的均速回推必须按其真实来源说明。
- 5 小时图两端显示开始时间与重置时间；周图两端显示开始日期时间与结束日期时间。倒计时放在用量条右侧，图例保持简洁。
- 图表保持无预测阴影、无额外平均虚线的当前设计，无新需求时不得恢复已移除的内容。宿主工具栏按宿主默认方式显示。
- 区间名称为“合理消耗区间”；“可持续”描述预算分配的目的。目的在于结合活跃习惯分配周额度，让每个完整 5 小时窗口的预算有参考价值。
- 历史样本必须直接来自已有记录，不得依赖面板打开频率。
- 历史处理必须仅使用计算所需的事件时间和限额字段，不得保存、输出或上传对话正文、认证令牌和账号敏感数据。
- 算法必须结合个人历史与人类日内活动，不区分工作日与周末。
- “合理消耗区间”必须表示完整 5 小时窗口的总预算；临近重置时不得把它改为剩余时间可用量。未完成回测时，不得把模型分位数表述为真实预测的概率保证。
- 更新时不得重启 Codex。安装文件、MCP 资源及宿主实际画面的版本必须分别检查。

## 实现入口与数据流

| 文件 | 当前职责 |
| --- | --- |
| [.agents/plugins/marketplace.json](../.agents/plugins/marketplace.json) | 本地市场清单，使用相对路径指向 `plugins/codex-usage-panel`。 |
| [plugin.json](../plugins/codex-usage-panel/plugin.json)、[mcp.json](../plugins/codex-usage-panel/mcp.json) | 插件身份、资源图标、Node stdio 服务与 `${PLUGIN_ROOT}` 入口。 |
| [server.mjs](../plugins/codex-usage-panel/server.mjs) | 启动本机 app-server 读取 `account/rateLimits/read`，扫描历史额度快照，提供工具与 HTML 资源。 |
| [pace-model.mjs](../plugins/codex-usage-panel/pace-model.mjs) | 线性预测、容量换算、个人日内时段学习及完整窗口预算区间。 |
| [data/human-rhythm.mjs](../plugins/codex-usage-panel/data/human-rhythm.mjs) | 通用日内活动先验与相关参数。 |
| [ui/index.html](../plugins/codex-usage-panel/ui/index.html) | 页面样式、历史曲线平滑、预测与区间绘制、时间轴、余量标签及刷新。 |
| [test/pace-model.test.mjs](../plugins/codex-usage-panel/test/pace-model.test.mjs) | 当前 25 项算法检查。 |

当前额度读取由本机 `codex app-server --stdio` 完成。服务扫描 `CODEX_HOME` 指定根目录下 `sessions/**/rollout-*.jsonl` 中的 `event_msg/token_count` 限额快照；未设置 `CODEX_HOME` 时，默认根目录为 `~/.codex`。历史最多回看 14 天；读取结果缓存在进程内 5 分钟。插件没有独立的历史采样数据库。

服务启动时将 `ui/index.html` 读入内存。更新源码或安装缓存后，现存服务返回的页面仍必须单独核查；页面中的用量刷新只说明数据请求发生，不能用来证明界面资源版本已经变化。

## 三种图表信息的语义

| 信息 | 含义与当前实现 |
| --- | --- |
| 绿色已用曲线 | 当前额度周期内的历史限额快照，经轻度平滑显示；数据不足时回退为当前窗口均速回推。 |
| 橙色线性预测 | 当前窗口已用比例 ÷ 已经过时间 × 窗口总时长；数值显示封顶 100%，窗口前 5 分钟暂不产生数字预测。 |
| 5 小时合理消耗区间 | 结合当前完整窗口所处时段、个人未来活跃窗口频率、额度换算与剩余周额度分配的总预算。当前已用量可以高于预算区间。 |

当前余量标签使用“重置时余量 N%”“重置前预计用尽”“重置时余量估算中”，取值仍以当前窗口的线性预测为依据。

0.1.29 的预算模型使用完整 `[5 小时重置时刻 − 5 小时, 重置时刻]` 的活动强度，结合本机近 14 天的活跃窗口和通用日内先验；星期几不参与。两个门槛分别检查：额度换算至少需要 4 个独立有效 5 小时窗口及合计 100 个百分点的 5 小时额度变化；活动时段估算至少需要近 14 天的 4 个有效活跃窗口，未满足时返回 `insufficient-activity-history`，区间暂不可用。额度换算样本不足或不稳定时也不生成区间。详细公式、工程参数和数据来源必须查看已有算法说明，并与当前代码相互核对。

## 开发、验证与更新

开发依赖支持 `node:test` 的 Node.js；真实额度读取还需要可用且已登录的 Codex CLI 与桌面端。以下命令必须在项目根目录执行：

```powershell
node --check ./plugins/codex-usage-panel/server.mjs
node --check ./plugins/codex-usage-panel/pace-model.mjs
node --check ./plugins/codex-usage-panel/data/human-rhythm.mjs
node --test ./plugins/codex-usage-panel/test/pace-model.test.mjs
```

验证记录包含上述语法检查和 **25 项算法测试**，另覆盖清单、页面内联脚本、MCP 初始化、两个工具的发现及 HTML 资源返回，也检查了从市场根目录启动服务时的页面资源定位。

本机市场可用 `codex plugin marketplace list --json` 检查，安装版本及启用状态可用 `codex plugin list --json` 检查。用户要求安装或更新时，按项目 README 的命令从该市场安装；必须保留现有身份，不直接改缓存。若新路径注册提示同名市场已存在于不同源，必须先核实旧源，再通过 CLI 移除旧登记并添加新登记；失败时必须恢复原源登记。

更新版本时必须一并核对清单版本、服务版本与 UI URI、页面 `appInfo.version` 及旧 URI 兼容列表。完成安装后必须检查资源返回；涉及界面的交付，还必须确认宿主里实际打开的页面。

### 修改与更新要求

- 算法变更必须执行现有算法检查，并针对变化验证预算语义、时区、重置顺序、异常样本和样本不足的处理。区间宽度与校准效果是待评估事项，仅在任务明确包含算法调整时，才可以修改算法。
- 服务或界面变更必须验证脚本语法、MCP 启动、工具发现和页面资源；界面交付还必须检查宿主内的实际画面。
- 涉及全局侧边栏图标或宿主工具栏时，必须先核实对应元素的当前接口和支持范围，再确定修改；不得把主图标或 Composer 图标的修改当作侧边栏入口已改变。
- 仅在用户要求安装、更新插件或任务明确包含该操作时，才可以安装或重装。更新过程中不得重启整个 Codex，必须分别核验安装状态、返回资源及已打开页面的版本。
- 验证必须按实际范围汇报；源码与缓存一致、资源能读取或测试通过，不得直接表述为已打开页面完成刷新或真实覆盖率已经验证。

## 待验证事项

- **预算区间宽度和校准效果仍待评估。** 当前 0.1.29 算法尚未完成真实使用窗口的覆盖率回测；后续算法修改必须有明确目标与验证依据。
- **25 项检查验证计算约束。** 当前仍没有真实使用窗口的覆盖率、误差或校准结果。第 10–90 分位表示模型情景的分散，实际准确率尚待验证。
- **宿主实际页面与真实额度读取须分别验证。** 上述 MCP 检查覆盖页面资源读取；不包含宿主实际画面和真实额度调用的复验。
- **侧边栏入口图标与宿主工具栏的支持范围待核验。** 后续涉及这些元素时，必须先检查当前宿主接口，再确定方案；`logo` 和 `composerIcon` 的资源修改必须按它们实际控制的元素验收。

**AI 后续建议：** 用户要求继续算法工作时，先确认区间要支持的使用判断，再用已有完整历史窗口回测当前模型，分别检查容量换算、活动时段、活跃窗口频率造成的误差及区间宽度。参数收窄必须有验证依据，具体方案需结合用户当时目标确定。
