# 开发说明

本文件记录 X 媒体工坊 Tauri 版（真实功能版）的技术实现、构建方式、真实验证记录与已知问题。使用操作见 [使用说明](./使用说明.md)，项目概览与截图见 [项目 README](../README.md)。

## 1. 项目定位与边界

- **真实功能版**：桌面后端由 Rust 重写，具备真实推文解析、媒体下载/保存、GIF/WebP 转换、外部工具下载、设置/历史、文件操作与代理能力；
- **单一桌面版**：前端源码与构建脚本均在本项目内，不再依赖 Electron 工程；
- **前端架构**：React/TypeScript 位于 `src/`，构建到 `dist/`，通过 `tauri-shim.js` 把 `window.desktop` 映射到 Tauri 命令；
- **平台**：仅 Windows 10/11 x64（依赖 WebView2、Windows 代理注册表、explorer、taskkill）。

## 4. 总体架构与数据流

```text
dist/（本项目 React 构建产物）
      │ prepare-dist.mjs：复制到本项目 dist/ 并注入 tauri-shim.js
      ▼
dist/  ──tauri build──►  release/XMediaStudioTauri.exe（前端资源内嵌）
                              │ 启动
                              ▼
                         WebView2（加载 dist/index.html）
                              │  window.desktop（shim）
                              │  invoke('command', args)
                              ▼
                         Rust commands
      ┌──────────────┬──────────┼──────────┬───────────┬────────────┐
      ▼              ▼          ▼          ▼           ▼            ▼
   tweet 解析    媒体下载/保存  GIF/WebP  工具下载   设置/历史   文件操作/代理
      │              │          │          │
      ▼              ▼          ▼          ▼
  fxtwitter 等   cache/media  cache/frames  <exe>/tools/
                 userdata/media、history.json、settings.json
```

- 数据目录：`<exe 目录>/userdata`（tauri.conf.json 的 `appDirectoriesOverride: "./userdata"`，与便携版行为一致）；
- 工具目录：`<exe 目录>/tools`（首次下载；也支持手动放置）；
- 本地文件显示：Tauri asset 协议（`convertFileSrc`），CSP 在复制出的 index.html 中放行 `asset: http://asset.localhost`；
- 远程图片（推文缩略图/头像）由 WebView2 直接加载，跟随 Windows 系统代理。

## 5. Rust 后端实现要点

### 5.1 推文解析（tweet.rs）

- `parse_tweet_url`：兼容 x.com/twitter.com、mobile/m/www、`/i/status/`、`/i/web/status/`、追踪参数与 `/photo/1` 后缀；
- 回退顺序：`api.fxtwitter.com/2/status/{id}` → `api.fxtwitter.com/{user}/status/{id}` → `cdn.syndication.twimg.com/tweet-result`（含 token 算法）→ `api.vxtwitter.com/i/status/{id}`；
- 归一化字段严格按 `src/shared/types.ts` 的 TweetInfo/TweetMedia：作者、正文、时间、媒体 kind（gif/video/photo）、sourceUrl（视频优先最高码率 mp4、图片取 name=orig）、thumbnailUrl、宽高、时长、variants；
- 明确区分「不存在 / 受保护 / 限流 / 网络失败 / 无媒体」，错误为可展示中文；
- 最近 20 条解析结果缓存在内存中，供保存/转换按 tweetId 取作者与媒体序号。

### 5.2 媒体（media.rs）

- `prepare`：缓存命中检查 → 流式下载到 `cache/media/<mediaId>.mp4`（带进度）→ MP4 探测 → ffmpeg 抽首帧生成 `cache/thumbs/<mediaId>.jpg`；
- `save`：优先复用 history 中已保存且文件存在的记录；输出到 `userdata/media/<screenName>/<tweetId>/`；视频复制缓存 mp4，图片按魔数识别 jpg/png/gif/webp 并解析宽高；写入 history.savedMedia；
- 缩略图接口 `media_video_thumbnail`：按「路径+大小+mtime」哈希缓存到 `cache/thumbs/saved/<hash>.jpg`；
- 图片尺寸解析：JPEG SOF、PNG IHDR、GIF 逻辑屏幕、WebP VP8X/VP8/VP8L。

### 5.3 GIF / WebP 转换（convert.rs + probe_*）

转换流水线：

1. 源媒体：优先使用 history 中已保存的 mp4；否则下载到 cache（autoSave 时先保存原文件）；
2. 抽帧：ffmpeg `-fps_mode passthrough`（fps=source 时保留全部帧、不重采样）或 `fps=N` 重采样；按参数宽度等比缩放；
3. 计算逐帧延时：fps=source 且 preserveTiming 时按 MP4 stts 逐帧时长对齐抽帧数，换算为 GIF 厘秒（累计取整、最小 2cs）；否则按总时长均匀分配；
4. GIF 编码：默认 gifski（`--no-sort --fps 名义帧率 --quality --repeat --width`），可选 ffmpeg 两遍调色板编码；
5. 延时还原：解析编码后 GIF 帧数，若与抽帧数不一致则按时间比例重新对齐；用 GCE 回写逐帧延时并处理 NETSCAPE 循环扩展，写回后读回校验；
6. WebP 编码：ffmpeg concat demuxer + `libwebp_anim`，编码后解析 ANMF，按目标毫秒改写逐帧时长并校验；
7. 可选 gifsicle `-O3 --lossy --colors`（默认关闭）；
8. 输出命名 `<screenName>_<tweetId>_<mediaIndex>_<W>x<H>_<preset|custom>_<时间戳>.<gif|webp>` 到 `userdata/media/<screen>/<tweetId>/`，结果写入 history.results。

参数来自前端设置（GifParams），后端逐项做范围收敛；当前前端构建未提供「预设」选择 UI，实际使用设置页保存的默认参数与抽屉里可调参数。

### 5.4 GIF 体积预估（estimate.rs）

背景：gifski 官方文档也说明其体积无法精确预测；同一源在不同 quality 下体积并非线性，
且 gifski 会对连续帧做差分裁剪（只编码变化区域），静态或缓变内容的后续帧几乎不占体积，
因此固定 bpp / 「源文件倍率」无法同时适配动画、实拍与合成内容（同一参数内容差异可达 2–3 倍）。
另外实测发现 gifski 逐帧体积依赖帧间状态的收敛：把帧从完整序列抽出来组成采样序列后，跨段跳变会让
后续 2–3 帧明显偏大（同一个「第二帧」在连续序列与采样序列里可差 50% 以上）。

实现（命令 `gif_estimate`，入参 `{ filePath, width, height, fps, quality, colors, encoder, durationSec, frameCount }`）：

1. 依据前端探测结果确定目标总帧数：优先 `frameCount`，其次 `durationSec × fps`，必要时后端探测源 MP4/GIF；
2. 总帧数 ≤12 时直接编码全部帧（样本即最终 GIF，返回精确值）；
3. 否则构造两个互补样本（样本 A 最多 12 帧；样本 B = 首帧 + 中段最多 9 帧）：
   - **样本 A（均匀段）**：取约 1/3 帧、最多 12、最少 3 帧，组织成 1–4 段连续帧段并均匀分布在全片，
     兼顾内容代表性；逐帧解析后按「首帧 + 稳态帧（剔除每段起始帧）均值 × (总帧数-1)」外推；
   - **样本 B（中段连续）**：首帧 + 中段一段连续帧，跳过前 2 帧暖机后取稳态均值外推，
     让 gifski 的差分/调色板状态充分收敛；中段长度上限 9 帧（1080p/4K 上降低 gifski 耗时且精度回归仍 <15%）；
   - 两个外推值取平均（model=hybrid）；只有一个可用时取单个（runs / mid）；
     都不可用（如重复帧被 gifski 合并）时退化为 `样本字节 × 总帧数 / 采样帧数`（naive）；
4. **抽帧改为分段 seek**：每段用 ffmpeg 输入侧 `-ss` 定位（时间来自 MP4 stts / GIF 逐帧延时累积的帧起始时间，
   再提前 1ms，保证首帧精确落在目标帧），只解码该段需要的少量帧；降帧率时先 `fps=` 过滤，
   再用 `select=lt(n,len)` + **`-frames:v len`** 精确截断——不加 `-frames:v` 时 ffmpeg 会继续解码到文件末尾，
   这是大文件慢 2–4 倍的主要原因；
5. **并发**：样本 A/B 用 `tokio::join!` 并发执行，样本内各连续段也并发 seek 抽帧（最多 4 段），
   两个 gifski 编码同时进行；
6. **结果缓存**：按 `(源路径, 源文件大小+mtime, width, height, fps, quality, encoder, colors, duration, frameCount)`
   在进程内缓存最近 8 条结果；源文件大小或 mtime 变化、参数变化都会生成新 key，命中直接返回（实测 <10ms）；
7. gifski 以目标 `--quality / --width / --fps` 编码样本 GIF，读取样本字节并解析逐帧图像数据大小；
8. 临时目录在返回或失败时自动清理；工具缺失/编码失败返回明确中文错误，前端回退经验公式。

**高分辨率代理（目标宽度 > 900px）**：4K 上 gifski 逐帧量化约 0.2s/帧，是全分辨率流程的主要瓶颈。
当目标宽度 > 900px 且目标像素数 ≥ 2× 高代理像素数（代理确实更省时）时：

1. 用两个代理宽度编码**同样的采样帧**：目标 > 1120px 用 800 / 1120 宽（实测 4K 外推误差最小），
   900–1120px 目标用 560 / 800 宽；
2. 代理抽帧用一次 ffmpeg 解码 + `split` + 两个 `scale` **双输出**同时得到低/高代理帧（避免重复解码）；
   代理模式采样简化为「2 段 × 6 帧的均匀段 + 首帧 + 中段 5 帧」，减少 seek 解码窗口；
3. 两个代理各算一遍 hybrid 整片预估字节 E，按 `E = k · pixels^α` 两点拟合
   `α = ln(E_high/E_low) / ln(pixels_high/pixels_low)`，再外推到目标像素数；
4. 异常保护：若 E 不随像素增长、α 不在 [0.5, 1.6]、外推倍率 >64× 或代理编码失败，
   自动回退全分辨率流程（结果 flags.proxy=false）；
5. 720p 等「目标像素相对高代理不足 2×」的目标代理反而更慢（实测 1280×720 全分辨率 1.8s vs 代理 2.0s），
   因此自动走全分辨率；900–1120px 目标在像素比不足时同样回退。

**预估模式（设置项 `AppSettings.estimateMode`）**：设置页「体积预估」提供四档，默认 balanced，保存后持久化：

| 模式 | 前端行为 | 后端行为 | 参考耗时 / 误差 |
| --- | --- | --- | --- |
| fast | 直接用 `estimateGifBytes` 经验公式，**不调用** `gif_estimate` | — | 0 秒 / 误差较大 |
| balanced | 有本地源时调用 `gif_estimate`（mode=balanced） | 采样编码 + 代理双尺度拟合 | 大文件 1–2 秒 / ±10–15% |
| precise | 有本地源时调用 `gif_estimate`（mode=precise） | **禁用 proxy**，按目标尺寸全分辨率采样编码 | 1080p 约 2 秒、4K 约 5–7 秒 / ±5–7% |
| off | 不调用、抽屉不显示 ≈ 体积 | — | — |

后端请求新增 `mode` 字段：`precise` 时跳过代理分支；`fast`/`off` 直接返回明确错误（前端不会调用）；
结果缓存 key 包含 mode（同一文件 balanced/precise 不会串结果）；结果 `flags.mode` 返回生效模式。
抽屉展示：balanced/precise 先「估算中…」再显示采样结果，fast 直接显示公式值，off 不显示体积估算。
设置页「体积预估」面板提供四模式说明与参考耗时/误差表（仅说明，不影响估算逻辑）。
公式校准（快速模式/回退）只使用 GIF 结果：WebP 体积与帧率不同，会严重污染快速模式估算。

该命令是**副作用只读的真实编码**：不写输出目录、不改历史，仅产生临时文件。
实测冷启动：3 秒短片约 0.4–0.6 秒；1080p/60s 约 1.2 秒；4K/20s 约 1.5 秒；缓存命中 <10ms（数据见 9.5 节）。
混合模型对纯合成内容（如生命游戏动画）误差仍可能超过 15%，详见第 9.4 节实测。

### 5.5 外部工具（tools.rs）

- 定位顺序：`<exe>/tools/{name}.exe` → `<userdata>/tools/{name}.exe`；
- 状态：运行 `ffmpeg -version`、`gifski --version`、`gifsicle --version` 取首行并缓存 10 秒；核心就绪条件为 ffmpeg + gifski；
- 一键下载源：ffmpeg（gyan.dev release-essentials zip）、gifski（gif.ski 1.32.0 zip）、gifsicle（eternallybored 1.97 win64 zip）；
- 下载：reqwest 流式写入 cache 临时目录（进度写入 tools_poll），纯 Rust ZIP 解压（stored/deflate，含路径穿越校验），递归查找 exe，运行 `--version` 校验后复制到 tools/，再校验一次；
- 已有可运行工具会自动跳过；临时目录结束即清理。

### 5.6 设置 / 历史 / 进度

- settings.json：读取时合并默认值并做白名单/范围收敛；保存前校验自定义代理地址；原子写入并保留 `.bak`；
- history.json：`{ version, entries: { tweetId: HistoryEntry } }`，按 lastOpenedAt 排序，savedMedia/results 增删，删除记录时可同时删除文件；原子写入并保留 `.bak`；
- 任务：每个 jobId 在 jobs.rs 登记进度；前端 shim 每 300ms 调 `jobs_poll` 拿快照并派发 onProgress；取消命令会标记取消并用 taskkill 终止进程树；
- 工具下载进度：独立 tools_poll 快照，shim 轮询派发 tools.onProgress。

### 5.7 网络与代理（http.rs）

- `direct`：不使用代理；
- `custom`：支持 http/https/socks5，支持用户名密码认证与 no_proxy 绕过列表（reqwest NoProxy）；
- `system`：读取 `HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Internet Settings` 的 ProxyEnable/ProxyServer（支持 `http=host:port;https=...` 格式）；未配置系统代理时直连；
- 未实现 PAC 脚本解析；代理认证密码以明文保存在 settings.json（生产使用建议后续改为 DPAPI 加密）。

## 6. 前端桥接（tauri-shim.js）

- `window.desktop` 字段与前端契约完全一致（isDesktop/app/tools/tweet/media/gif/history/settings/proxy/jobs/clipboard/window）；
- 所有方法通过 `window.__TAURI_INTERNALS__.invoke(command, args)` 调用 Rust；
- `media.toDisplayUrl` / `videoThumbnail`：本地路径转 Tauri asset URL；远程 https 原样返回；
- `media.probeFile`：调用 `media_probe_file`，非 mp4 返回 null；
- `gif.estimate`：调用 `gif_estimate`（采样编码体积预估），抽屉/结果卡有本地源路径时由前端 debounce 500ms 调用；
- 进度：`jobs.onProgress` / `tools.onProgress` 用 setInterval 轮询 `jobs_poll` / `tools_poll`，订阅数为 0 时自动停止；
- 窗口：最小化/最大化/关闭/拖动调用同名 Tauri 命令；无边框拖动由 shim 监听标题栏 mousedown + 4px 阈值后调用 `window_start_drag`；
- 剪贴板：复制路径使用 `navigator.clipboard.writeText`。

## 7. 构建与运行

前置：Windows 10/11 x64、Node.js 22+、npm 11+、Rust 1.77.2+、能访问 crates.io（受限网络请配置 Cargo 镜像/代理）。前端源码与构建脚本已在本项目内。

```powershell
cd x-gif-studio-tauri
npm install
npm run prepare:dist   # 复制 dist + 注入真实 shim + 放行 CSP
npm run build          # tauri build --no-bundle + copy-release
npm run capture        # 真实功能验证与截图（需要 tools/ 三个工具）
npm run dev            # Tauri CLI 内置静态服务器加载 dist（改前端后需重新 prepare）
```

- 产物：`release/XMediaStudioTauri.exe`；

### 9.5 GIF 体积预估性能验证（2026-11-16）

测试视频（ffmpeg testsrc2 生成）：

- 1080p：1920×1080、30 fps、60 秒（1800 帧，libx264 ultrafast CRF28，约 81 MiB）；
- 4K：3840×2160、30 fps、20 秒（600 帧，约 89 MiB）。

通过 release exe 的 WebView2 CDP 调用 `window.desktop.gif.estimate`（quality 92、尺寸=源尺寸、fps=源帧率）：

| 场景 | 最初（整片解码 + 顺序编码） | seek + 并发 + 缓存 | 代理双尺度（当前） | 当前缓存命中 |
| --- | --- | --- | --- | --- |
| 1080p 60s（1800 帧） | 3,831 ms | 1,894 ms | **1,183 ms** | 3 ms |
| 4K 20s（600 帧） | 8,122 ms | 5,298 ms | **1,539 ms** | 3 ms |

> 数字来自 Rust 返回的 `elapsedMs`，均为同机冷启动首次调用。1080p 60s 与 4K 20s 均 <2 秒（4K 相对最初 −81%）。

**代理双尺度精度**（全量帧用同一 gifski 参数编码作为「实际」，代理估算为 release exe 真实返回）：

| 目标 | quality | 代理估算 B | 实际编码 B | 误差 | 拟合 α |
| --- | --- | --- | --- | --- | --- |
| 1080p 1920×1080 / 300 帧 | 92 | 32,915,092 | 32,537,900 | +1.2% | 0.930 |
| 1080p 1920×1080 / 300 帧 | 50 | 19,242,470 | 17,090,117 | +12.6% | 0.988 |
| 4K 3840×2160 / 300 帧 | 92 | 128,094,883 | 125,011,998 | +2.5% | 1.015 |
| 真实推文视频 1280×720 / 76 帧 | 92 | 14,637,104 | 13,058,059 | +12.1% | 回退全分辨率 |

> 代理拟合在 800/1120 两档上测量整片预估字节，外推到目标像素；1280×720 目标像素仅为高代理的 1.31×，
> 代理编码反而更慢（实测 ~2.0s vs 全分辨率 ~1.8s），因此按「目标像素 ≥ 2× 高代理像素」自动回退全分辨率。

关键优化：

1. **输入侧 `-ss` 分段 seek**：按 MP4 stts / GIF 逐帧延时算出每段起始时间，只解码该段需要的少量帧，替代「整片解码 + select」；
2. **`-frames:v <len>` 截断**：首版 seek 方案单段仍需解码到文件末尾（实测单段 0.4–0.77s），加上输出帧数限制后降到 0.11–0.18s；
3. **并发**：A/B 两个样本用 `tokio::join!` 并发，样本内最多 4 段并发抽帧，多个 gifski 编码同时进行；
4. **中段样本长度上限 9 帧**（代理模式 5 帧）：gifski 编码是主要耗时来源，缩短中段样本可感知降低大分辨率耗时；
5. **进程内结果缓存**：最近 8 条，key 含源 mtime/size 与全部参数，同参数重复调用 <10ms（抽屉重新打开/拖动后回到原参数时直接命中）；
6. **代理分辨率双尺度拟合**（目标宽度 >900px 且像素收益足够）：800/1120 两个代理宽度编码同样采样帧，
   用 `E = k · pixels^α` 两点幂律拟合后外推到目标像素；异常（α 越界、E 不随像素增长、外推 >64×）回退全分辨率；
7. **双输出代理抽帧**：一次 ffmpeg 解码 + `split` + 两个 `scale` 同时产出低/高代理帧，避免重复解码；
   代理模式采样简化为「2 段 × 6 帧均匀段 + 首帧 + 中段 5 帧」进一步减少 seek 解码窗口。

长视频精度补充回归：60 秒 360p/1800 帧合成视频（目标 ≤900px，走全分辨率路径）全量编码
q50 = 16,357,375 B、q92 = 35,101,995 B；采样预估 q50 = 16,581,598 B（+1.4%）、q92 = 33,781,803 B（−3.8%）；
冷启动 0.60/0.55 秒、缓存命中 2ms。说明「抽样子集外推到数千帧」的模型在长视频上仍然成立。

## 10. 已知问题与未完成项

- 当前前端构建未提供 GIF 预设选择 UI（GIF_PRESETS 定义仍在共享代码中），转换使用设置页默认参数 + 抽屉可调参数；如需预设 UI 需直接修改本项目前端；

- 外部工具下载仅验证了 gifski；ffmpeg/gifsicle 使用同一代码路径但未重新下载验证（本机已有）；
- gifsicle 有损优化（optimize=true）路径未纳入自动验证；
- GIF 体积预估依赖「源媒体已保存/缓存到本地 + 编码器为 gifski + 未启用 gifsicle 优化」；WebP / ffmpeg 编码 / 无本地源时仍显示经验公式；
- 采样预估对「重复帧被 gifski 合并」的内容（如静态画面）会退化为均值外推，误差可能偏大；对帧间变化极不均匀的合成内容（如生命游戏动画）实测误差可能超过 15%；
- 高分辨率代理拟合（目标 >900px）依赖「体积随像素近似幂律」的假设：实测 1080p/4K 误差 1–13%，但内容差异大时仍可能超 20%；
  目标像素不足高代理 2×（如 720p）、拟合异常（α 越界/E 不随像素增长）或代理编码失败时自动回退全分辨率（更慢但更稳）；
- 任务取消、另存为对话框、打开/定位文件未纳入自动验证；
- 代理认证、系统代理异常场景未纳入自动验证；不支持 PAC 脚本；
- 转换 4K/长视频时会把全部帧以 PNG 写入 `userdata/cache/frames`，磁盘/内存占用大且不会自动清理（转换结束会删除本次帧目录，异常退出可能残留）；
- 历史文件与设置文件已做 .bak 备份但仍无版本迁移机制；
- 未做代码签名、安装包与自动更新；
- 仅 Windows 10/11 x64 验证，Linux/macOS 未适配。
